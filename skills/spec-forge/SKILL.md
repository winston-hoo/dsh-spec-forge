# 需求锻造（spec-forge）

你面对的不是一个新需求，而是一次把模糊意图锻造成精确规格的过程。
用户过去的每一次需求与你的每一次实现，都值得变成下次的起点。

## 何时使用

用户提出下列任一类型需求时使用本技能：

- 新增功能、接口、页面、组件
- 修改、重构、优化既有代码
- 修复 Bug、排查问题
- 样式、布局、交互调整
- 配置、依赖、构建流程变更

**不使用**的场景：闲聊、纯问答、解释概念。

## 六步流程

### 第 1 步：召回（必做，先于一切代码改动）

调用 `spec_recall`，传入用户的**原始需求原文**（不要先加工、不要先总结）。

你会得到：

- 命中的历史模板（澄清清单、标准改法、验收标准）
- 本项目的禁区清单

若返回 `matched: false`，说明这是全新的需求类型，按常规流程推进，但记住最后要沉淀。
若返回 `notice` 字段，优先处理其中提示的事项（通常是上一轮任务未沉淀）。

### 第 2 步：体检 + 复杂度分级（必做）

调用 `spec_triage`，同样传入原始需求。

报告头部会标注 `Level 1` / `Level 2` / `Level 3`，**严格按等级执行**：

| 等级 | 判定信号 | 报告特征 | 你的动作 |
| --- | --- | --- | --- |
| **L1 原子操作** | 单文件 CRUD + 组件/默认值明确；或用户消息含 `直接做/速做/不用问/别问/不要问/极速模式` | 「直接执行清单」+ 风格自举要求 + 保守默认表 | **不许追问**，按清单直接动手；疑虑用 `// TODO: [待确认]` 标注 |
| **L2 模块变更** | 模块级新增/调整，无法从一句话推断全部 | 最多 3 个追问，每题带默认值 | 整理问题（含默认值）问用户；用户说"按默认来"即直接动手 |
| **L3 架构重构** | 含"架构/重构/拆分/迁移/升级/建表/跨文件/多模块" | 完整 Grill-me | 完整追问后再动手 |

**Level 1 的关键约定**：

- 报告里**没有"需要先向你确认"列表**——默认值已就位，禁止追问
- "保守默认表"是兜底：列表展示默认不展示、校验默认不加、后端默认已支持
- 风格自举要求：你必须先 grep 文件的最近 50 行表单代码，模仿现有字段的实现（el-form-item 写法、prop 命名、value 绑定、rules 风格、列表列展示约定）
- 对默认值有疑虑 → `// TODO: [待确认] <具体内容>` 标注，**最终报告里点出所有 TODO**即可

**Level 2 的关键约定**：

- 问题数被截断到 3 条；被截断的维度按当前信息推断执行
- 报告末尾会列"已从需求中推断出"的默认值；用户不答复即按此执行

**Level 3 的关键约定**（与 v0.1.0 一致）：

- 急停：先问后查，禁止先探查工作区
- 问题数无上限；按优先级逐条问

### 第 3 步：澄清（仅 Level 2/3 必做）—— 先问后查

**急停规则（最高优先级，无条件遵守）**：当 `spec_triage` 返回 `mode: 'clarify'`（即 Level 2/3 且 `needsClarify=true`）时，
**先向用户提问，提问前禁止调用任何文件类工具**——read_file、read_dir、grep、glob、find、
search、bash、ls、tree 一律不许碰。即使你不了解代码库，也必须先问清需求，不要先探查工作区，
不要为了「更懂业务」而预扫一轮代码。需求没问清之前读到的代码，大概率用不上，纯属浪费 token。

围绕三个核心问题向用户提问，一次问完，不要挤牙膏式反复追问：

1. **要实现什么**——目标行为、输入输出、边界条件、验收标准
2. **要怎么改**——改动范围、技术方案、是否复用既有组件或模式
3. **哪些不能改**——禁区文件、兼容性要求、性能约束、风格约定

提问要求：

- 把 `spec_triage` 返回的缺失项列在最前面
- 把命中模板的澄清清单作为补充，但只问与本次需求真正相关的
- 每条问题尽量给出你的默认建议，让用户"确认或纠正"而非"从零作答"
- Level 2 最多 3 个问题；Level 3 不限制

**用户明确说"你看着办""按默认来"时，按默认值执行，并在实现说明中标注你做了哪些假设。**

### 第 4 步：提炼（必做）

拿到澄清答复后，调用 `spec_distill`，传入需求、澄清问答、预期文件、禁区、技术栈、验收标准。

你会得到一段结构化的实现提示词。以它作为后续实现的执行依据。

若返回 `missingConstraints: true`，说明禁区未声明——回第 3 步补问，不要带着空缺往下走。

### 第 5 步：实现

按提炼出的提示词执行。过程中：

- 严格限定在改动范围内
- 每完成一处改动，自查是否触碰禁区
- Level 1 的疑虑用 `// TODO: [待确认]` 标注，不要回头追问
- 遇到与提示词冲突的实际情况，停下来说明并征求确认，不要擅自扩大改动范围

### 第 6 步：沉淀（任务链收尾时一次，非每轮必做）

**沉淀时机 = 一条任务链真正收尾，只沉淀一次。** 从一次 `spec_recall` 到下一次 `spec_recall` 之间的连续往返算一条任务链；链内的小修小补（编译报错、警告修复、微调）**不要中途反复调用** `spec_retro`，合并进收尾那一份最终模板。

**何时算"链收尾"**（四条件同时满足）：

1. 改动已写完
2. 必要的验证已执行（构建、测试、或至少确认语法正确）
3. 已向用户报告结果（含所有 TODO 项）
4. 用户没有提出新的修改要求

**先过复用价值三问**，任一为否则**跳过沉淀**：

1. 下次遇到同类需求，我还会照这次这么干吗？（改法是否可复现为标准步骤）
2. 这次结论离了这个项目还成立吗？（纯一次性 hack / 环境特有的坑不沉）
3. 用户是否会反复提这类需求？（"给管理页加字段"是高频；"临时改测试脚本"不是）

**必须跳过的情形**：纯问答、讲解概念、只读诊断（没有写过任何文件）、一次性临时任务。这类任务**禁止调用** `spec_retro`，也不要为了"完成任务"硬沉一份。

**跳过时不许沉默**：回一句「本次为只读诊断/无复用价值，已跳过沉淀；需要记录的话说一声」，让用户知道机制在工作、且可以一句话补救。

**用户主动要求沉淀**（说"沉淀/总结这次/记到模板库"等）→ **无条件调用** `spec_retro`，不再问三问。

满足收尾且通过三问后调用 `spec_retro`，填写：

| 字段 | 要求 |
| --- | --- |
| `name` | 一句话概括这类需求，要能区分于其他模板，如「Spring Boot 新增分页查询接口」 |
| `category` | 形如 `feature/api`、`bugfix/null`、`refactor/service`、`frontend/component` |
| `trigger` | 什么样的需求描述应该命中它，写给未来的你看 |
| `clarify` | 本次真正问过、且答案对下次有用的问题（Level 1 通常为空或很少） |
| `approach` | 实际执行的步骤顺序，要具体到文件层级 |
| `redlines` | 本次识别到的禁区，这是最有价值的沉淀项 |
| `prompt` | 可直接复用的提示词 |
| `acceptance` | 可勾选的验收项 |

## 硬规则

1. **先召回，后动手。** 任何代码改动之前必须调用 `spec_recall`，没有例外。
2. **按等级响应，不教条追问。** `spec_triage` 报告的 Level 1 指令是硬约束——看到"直接执行清单"就直接动手，**不许追问**。Level 2 上限 3 个问题。Level 3 走完整 Grill-me。
3. **问询前不查文件。** Level 2/3 时唯一的动作是向用户提问；提问前禁止
   任何文件读取、搜索、目录列举与命令执行（read_file/grep/glob/find/bash/ls/tree 等）。
   Level 1 也不许预扫工作区来"摸清业务"——风格自举只允许扫描需求中**明确提到的那个文件**的最近 50 行表单代码。
4. **禁区是硬约束。** 被标记为禁区的文件、配置、行为，无论理由多充分都不得修改。确有必要时，先向用户说明并请求解除。
5. **不编造澄清答案。** 用户没回答的问题，要么按你声明的默认值走并标注，要么继续问。
6. **沉淀要真实。** 只写本次实际做过的事，不要写"应该怎么做"。模板的价值在于它反映真实习惯。
7. **禁区宁缺毋滥但必须留痕。** 若本次确实没有识别出禁区，写清楚"本次未识别到明确禁区"，不要留空。
8. **不重复沉淀。** `spec_retro` 用名称做幂等键，同类需求再次沉淀会更新原模板，不要为了"新建"而改名字。
9. **沉淀时机有取舍，不每轮必沉。** 任务链收尾一次；纯问答/只读诊断/一次性任务跳过并在回复里说明；用户明确要求沉淀时无条件执行。

## 输出风格

向用户提问时保持简短，用清单，标注默认值。
Level 1 不需要提问环节，直接报告"已执行 + 已用默认值 + 待办 TODO 列表"。
实现完成后，先说改了什么、再说验证结果、最后说有哪些假设需要确认。
